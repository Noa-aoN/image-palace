# ADR: スペース（ロード／ルーム）とビュー「スペースマッピング」の設計

- **日付**: 2026-06-18
- **ステータス**: 承認済み（設計合意。実装は段階的に着手）
- **決定者**: チーム

---

## コンテキスト

記憶の宮殿（場所法・連結法）的な空間機能を整理する。
「スペース」を **カードなど覚えたいものを置く"場所"** として再定義し、
その場所を作る単位（ロード／ルーム）と、そこへカードを配置する手段（ビュー）を分離して設計する。

既存の実装（MVP後の骨格として実装済み）:

- `spaces`（`space_type` = `road` / `room`）、`space_points`（`position`=序数, `item_id`=任意）
- `space_collections`（room=コレクション棚）
- `views`（`view_type` = freeboard ほか。freeboard のみ実装）、`view_items`（`x`/`y`/`z_index`）
- 画像生成基盤: `GenerateImageService` / `GenerateImageJob` / `NormalizePromptService` / `PromptBuilderService` / `shared_media` キャッシュ / R2

`docs/OS.md`（コア設計書）はディスク上に存在しないため、本ADRが当面この領域の設計の正本となる。

---

## 用語・概念

- **スペース** = 記憶対象（カード等）を置く「場所」のテンプレート。再利用可能。
  - **ロード（road）** と **ルーム（room）** は **別項目（別種別・別の作成導線・別の詳細画面）** として提示する。
    データ基盤（`space_points`）は共有するが、プロダクト上は統合せず別物として扱う。
- **ポイント（loci）** = スペースを構成する要素。各ポイント = `序数(position)` + `ポイント名(name)` + `生成画像`。
  - **road**: ポイントを序数順に並べる（連結法）。
  - **room**: ポイントに `x`/`y`（間取り座標）を持たせて配置する。
- **ビュー「スペースマッピング」** = 配置インスタンス。作成済みスペースを1つ選び、その各ポイントにカードを割り当てる。

---

## 決定

### 1. カードの配置情報は「ビュー側」に持たせる

- スペースは **ポイント定義のテンプレート**（名前・画像・road順序／room間取り）に徹する。
- ビュー（`space_map`）が **「どのスペースを使い、どのポイントにどのカードを置くか」** を保持する。
- これにより **同じスペースを複数ビューで再利用** できる。
- 現状の `space_points.item_id`（ポイントに直接カード）は配置がビュー側へ移るため不使用化（将来 drop）。

### 2. ロードとルームは別項目。基盤の `space_points` は共有

- `space_type` の `road` / `room` を維持し、UI・作成導線・詳細画面は分ける。
- 両者とも `space_points`（序数＋名前＋画像）を基盤に使う。room はさらに `x`/`y` を持つ。
- 既存の `space_collections`（room=棚）は当面据え置き、段階的に縮小。

### 3. ポイント画像は月間生成上限（月100枚）をカードと共有して消費

- ポイント画像も OpenAI 生成＋`shared_media` キャッシュを使い、既存の生成パイプラインを流用。
- 生成数カウントを `items` と統一し、ポイント生成も月100枚枠を消費する。

---

## データモデル変更（方針）

1. **`space_points` 拡張**
   - 追加: `name`（ポイント名）、`x`/`y`（room用・nullable）、ActiveStorage 画像＋生成ステータス/metadata（`items` と同型の生成フロー）。
   - 生成: ポイント名 → `PromptBuilderService` / `NormalizePromptService` → `GenerateImageJob` → `shared_media` → R2。
2. **ビュー↔スペース紐付け＋配置**
   - `views` に `space_id`（nullable、`space_map` 時必須）、`view_type` に `space_map` を追加。
   - 配置は既存 `view_items` に `space_point_id`（nullable）を追加して流用（推奨）。
     `space_map` では「どのポイントにどのカード」を表し、座標はポイント由来。freeboard は従来どおり `x`/`y`。
3. `space_collections` は据え置き（段階的縮小）。

> マイグレーションは既存ファイルを編集せず新規追加する。staging 先行 → 動作確認 → production の順を守る。

---

## 段階的実装プラン（ロードマップ 5/18–5/24 に合致）

- **Phase 1**: `space_points` に `name` ＋ 画像生成。road の作成/詳細 UI で「序数・名前・画像生成」。
- **Phase 2**: room の間取り対応（`x`/`y` ＋ ドラッグ配置 UI）。
- **Phase 3**: ビュー「スペースマッピング」（`space_map` 種別・スペース選択・ポイントへカード配置 UI）。
- 各フェーズで RSpec ＋ 型/lint、PR を分割。

---

## 影響

- サイドバー: 「スペースマッピング」はビューの一種。先のサイドバー整理（ページ系／作成系）はそのまま有効。
  導線は「ビュー作成 → 種別: スペースマッピング」。ロード／ルームは別項目として独立。
- コスト: ポイント画像が月100枚枠を消費するため、生成数表示・上限チェックの集計に `space_points` を含める必要がある。
- 既存 `space_collections` ベースの room は当面共存。
