# ADR: バックエンドインフラ選定

- **日付**: 2026-03-17
- **ステータス**: 承認済み
- **決定者**: チーム

---

## コンテキスト

MVP フェーズのバックエンドをどこにホストするかを決定する必要がある。
要件：

- Rails 8 API + ActiveJob + Redis が動作すること
- Dockerfile ベースでのデプロイが可能なこと
- 初期コストを最小化（月額 $0〜$25 程度）
- 将来のスケールアップ時に移行コストが低いこと

---

## 検討した選択肢

### A. Render
- **メリット**: free tier あり、GitHub 連携が簡単、PostgreSQL アドオンも利用可
- **デメリット**: free tier はスピンダウンあり（コールドスタート数十秒）

### B. Railway
- **メリット**: Dockerfile そのまま動作、開発者体験が良い、プレビュー環境が容易
- **デメリット**: free tier が Render より少ない

### C. Fly.io
- **メリット**: エッジデプロイ可能、無料枠あり
- **デメリット**: 学習コストが高め

### D. Cloud Run（Google Cloud）
- **メリット**: スケールゼロ〜大規模まで対応、コンテナ直接デプロイ
- **デメリット**: IAM・VPC 等の設定コストが高く MVP には過剰

---

## 決定

**MVP フェーズ: Render または Railway を選択する（どちらでも Dockerfile があれば移行可能）**

移行トリガー（以下のいずれかを満たしたら Cloud Run へ移行）:
- 月額コストが $100 を超えた
- 月間リクエスト数が急増し Render/Railway のリソース上限に達した
- レイテンシ要件が厳しくなりエッジ・リージョン選択が必要になった

---

## 理由

- Dockerfile さえ整備されていれば Render → Railway → Cloud Run の移行コストは数時間
- MVP では速度・コスト優先のため、設定が最もシンプルな Render/Railway を使う
- Cloud Run は移行先として明示的に設計に組み込んでおくことで、スケール時の意思決定を迷わない

---

## 結果・影響

- `infra/` に `Dockerfile` および `docker-compose.yml` を整備する（ローカル・本番共通）
- 環境変数は Render/Railway のダッシュボードで管理（`.env` はコミットしない）
- DB は Neon（PostgreSQL サーバーレス）を使用し、バックエンドホストと独立して管理
