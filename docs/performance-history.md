# 速度改善の軌跡（2026-08-11）

ページの読み込みと遷移が重い、という相談から始めた調査と、その結果。
「何をしたか」より **「なぜそう判断したか」** を残す。次に遅くなったときに
同じ順路を辿れるようにするため。

やり方の手順は [performance-tips.md](./performance-tips.md) に分けた。

---

## 1. 結論から

**遅さの正体は SQL の質ではなく、往復の本数 × 距離だった。**

Fly(nrt) から Neon(ap-southeast-1) まで**片道 70ms**。この構成では、
index を足しても意味がない。1本のクエリが 70ms かかるなら、11本で 770ms になる。
実際、最も遅いクエリでも 140ms、大半はちょうど 70ms（＝純粋な往復時間）だった。

だから打ち手は2つしかなかった。

1. **往復の本数を減らす**（N+1 を潰す・同じ数を数え直さない）
2. **距離を詰める**（アプリを DB の隣へ移す）

どちらもやった。Redis も Sidekiq も、有料の東京DBへの移行も要らなかった。

---

## 2. 実測値（すべて本番データ）

### 距離

| | nrt（東京） | sin（シンガポール） |
|---|---|---|
| DB往復 中央値 | **70.2ms** | **2.4ms** |
| 最小 / 最大 | 70.0 / 73.0ms | 2.1 / 5.5ms |

20回計測。nrt 側は最小と中央値がほぼ同じ＝純粋なネットワーク遅延で、
DB の負荷ではないことが分かる。

### エンドポイント（同じコードを両リージョンで実行）

| 処理 | nrt | sin | 倍率 |
|---|---|---|---|
| 実績の評価（25本） | 4393ms | **468ms** | 9.4× |
| ボックス一覧（9本） | 1357ms | **297ms** | 4.6× |
| ダッシュボード（6本） | 505ms | **39ms** | 12.9× |
| キャンバス一覧（3本） | 494ms | **58ms** | 8.5× |
| スペース一覧（3本） | 301ms | **23ms** | 13.1× |
| 読みもの一覧（1本） | 217ms | **17ms** | 12.8× |

**1クエリしかない「読みもの一覧」ですら 12.8 倍**。これが、距離が効いている
何よりの証拠になった。

### 改善の総まとめ

| | 改善前 | 改善後 |
|---|---|---|
| DB往復 | 70.2ms | **2.4ms** |

**追加の月額費用はゼロ。**

## 3. 調査した順番

順番そのものが資産なので、辿った道を残す。

### ① まず外側から測った（無料・非破壊）

- 主要ページの TTFB を curl で計測 → **120ms 前後。フロントは犯人ではない**
- CDN の画像を GET で確認 → `cf-cache-status: HIT` / `immutable` / WebP。**画像も犯人ではない**
- 静的ファイルのヘッダを確認 → **`max-age=0, must-revalidate` を発見**（後述）
- JS の総量を計測 → `/items` で brotli 後 491KB。重いが致命的ではない
- three.js（876KB）が全ページに載っていないかを確認 → `/spaces/[id]` のみ。**問題なし**

**ここまでで「フロントではない」と切り分けられたのが大きい。**
以降は API と DB に集中できた。

### ② 本番DBに対して直接測った（worker機で・読み取りのみ）

`fly machine exec` + `bin/rails runner` で、
`ActiveSupport::Notifications.subscribe("sql.active_record")` を使って
**本数と各SQLの時間**を採った。

ここで `SELECT 1` を20回打って **70ms** という数字が出た瞬間に、
調査の性格が変わった。「遅いクエリを探す」から「往復を数える」へ。

### ③ 見つかった N+1 を潰した

### ④ 距離を詰めた（最後）

**構成を変えるのは最後**にした。先にコード側を直しておかないと、
リージョンを移した効果と混ざって切り分けられなくなる。

## 4. 実施した改善

### 4-1. カード一覧の N+1（PR #530）

**82本 5583ms → 11本 205ms**

- **サムネイル添付（`thumb`）を eager load していなかった。**
  1枚ごとに「サムネある？」「その実体は？」で2往復増え、24枚で約50往復。
  読む対象を `Item::MEDIA_INCLUDES` に集約し、全一覧へ適用。
- **読み込み済みの `meanings` に `.ordered` を当てていた。**
  スコープを挟むと `includes` 済みでも問い合わせが1本増える。
  `Item#sorted_meanings` でメモリ上の並べ替えに変更。

### 4-2. 静的ファイルのキャッシュ（PR #530）

Cloudflare Workers Assets の既定は `cache-control: public, max-age=0, must-revalidate`。
**中身のハッシュが名前に入っているビルド成果物まで、毎回聞きに行っていた**
（カード一覧なら JS だけで25本）。

`frontend/public/_headers` を追加し、`/_next/static/*` を `immutable` に。

### 4-3. トップページの画像（PR #530）

ヒーロー画像一式を WebP へ。**929KB → 463KB**。

### 4-4. 実績の評価（PR #531 / #532）

**144本 16.7秒 → 18本 1.5秒**。`/achievements` を開くたび同期で走っていた。

- 条件の種類は8つしかないのに、**定義ごとに数え直していた**
- 実績・ミッションの行を**定義ごとに `find_or_create_by!`** していた
  → まとめて読み、足りないぶんだけ `insert_all`
- `DISTINCT DATE(reviewed_at)` を**1回の評価で5回**引いていた
  → `Streak.summary` で日付一覧1回から3つとも出す
- `UserStat.recompute!` が評価の直後に**同じ COUNT を数え直していた**
  → `counts:` / `streak:` で渡す

### 4-5. アプリを sin へ寄せた（PR #533）

**これが最大の一手。** 詳細は §5。

### 4-6. 一覧APIの payload（PR #534）

**18.8KB → 12.2KB。** カード一覧が1枚ごとに詳細と同じ中身
（項目定義一式・意味の全件・画像への指示・ファクトチェックの根拠）を返していた。
一覧が実際に読むのは12項目だけ。`serialize_list_item` を新設。

Wikipedia の項目が入ってからは、抜粋の長さがそのまま一覧の重さになっていた。

### 4-7. サムネイルのバックフィル

サムネイルの無い画像22件のうち、実体のある17枚を生成。
**該当19件で 18.06MB → 493KB**。元画像には触れず、追加のみ。

実体の無い3件（`generation_status = failed`・R2 に無い）はスキップして記録した。
**削除はしない**方針を守った。

## 5. なぜ app を sin へ寄せたのか

### 前提の誤りを1つ訂正した

最初、私は「Neon を東京へ移す」と提案した。**これは誤りだった。**
指摘を受けて公式のリージョン一覧を確認したところ、

> Neon の AWS 8リージョンのうち **Asia は Singapore と Sydney のみ。東京は存在しない。**
> （Azure の3リージョンは新規作成停止＝廃止予定）

つまり **DB は既に、Neon で東京に最も近い場所にあった。**
Neon 内での移設に改善の余地はゼロだった。

**教訓: 提案の前に一次情報を確認する。** 記憶で「あるはず」と書かない。

### 距離は相対的

DB を動かせないなら、**アプリが DB の隣へ行けばいい**。

- ブラウザ → API の1往復は **+55ms 増える**
- API → DB の **N 往復が実質消える**（70ms → 2.4ms）

N ≥ 1 なら差し引きで勝つ。実測では 1クエリのエンドポイントでも 217ms → 17ms だった。

フロントは Cloudflare Workers（全世界のエッジ）なので HTML 配信は無関係。
画像も R2 + CDN で無関係。**影響を受けるのは「ブラウザ→API」の1往復だけ。**

### 移設の手順（無停止に近い形）

worker が2リージョンで同時に動く瞬間を作らないことが肝。

1. sin に app を作る（この時点で日本のユーザーは近い nrt に流れたまま＝無影響）
2. sin app の health を単体で確認
3. **nrt worker を止める**（この時点で sin worker はまだ存在しない）
4. nrt app を止める ← **切替点**（数秒）
5. sin に worker を作る
6. nrt standby を破棄
7. `fly.toml` の `primary_region` を `sin` へ
8. soak 後に nrt を破棄

**nrt はすぐ破棄せず、停止のまま残した。** rollback を `machine start` で
即座にできる状態を維持するため。破棄は動作確認が済んでから。

### 副作用として分かったこと

- 定期ジョブは**切り替えの谷間の tick を取りこぼす**（backfill されない）。
  実際 11:00 の `RecoverStuckGenerationsJob` が1回飛んだ。実害は無かったが、
  次回は「その5分間に何が走る予定か」を先に見ること。
- `Rack::Attack` の `req.ip` は Fly proxy のヘッダ由来なので**リージョンに依存しない**
- Stripe webhook は anycast の `api.imagepalace.app` 宛なので**設定変更不要**

## 6. なぜ Redis / Sidekiq / 東京DB移行ではなかったのか

### Redis

**ボトルネックはキャッシュの不在ではなく、往復の距離だった。**
Redis を足しても、それが第三の地域にあれば往復が増えるだけ。
「キャッシュがあれば速くなる」は、キャッシュが近くにある場合の話。

Redis を検討すべき条件（今回はどれも当てはまらなかった）:
- Solid Queue が明確に DB を圧迫している
- キューのスループットが足りない
- ジョブ数の増加で DB 接続が詰まっている
- SQL・index・payload 削減では改善しきれない

### Sidekiq

**Solid Queue は原因ではなかった。** worker は既に別プロセス・別マシンで
分離済みで、`SOLID_QUEUE_IN_PUMA` は未設定だった。Web を圧迫していない。

（過去に `SOLID_QUEUE_IN_PUMA` で同居させて API がハングした経緯があり、
それは #339 / #340 で解決済み。今回それが再発していないことも確認した）

### 東京DBへの移行

比較した結果、**費用に見合わなかった**。

| | 月額 | 移行工数 | 運用負荷 | Fly(nrt)から |
|---|---|---|---|---|
| **app を sin へ**（採用） | **±0** | 数十分 | 変化なし | DB往復 2.4ms |
| Fly Managed Postgres `nrt` | +$38〜 | 半日 | 低 | 1ms未満 |
| Supabase Tokyo | +$25 | 半日〜1日 | 低 | 数ms |
| AWS RDS `ap-northeast-1` | +$20前後〜 | 1〜2日 | **高** | 数ms |
| Aurora Serverless v2 Tokyo | +$45前後〜 | 1〜2日 | **高** | 数ms |

DB は **17MB・13ユーザー**。この規模で月 $25〜45 を足すのは、
`±0` で同等の効果が得られる選択肢がある以上、割に合わない。

**将来 Neon が東京を出したら、`primary_region` を戻すだけで nrt へ帰れる。**

## 7. 副産物：見つかったバグ

### 空白を含む語で Wikipedia が引けない（PR #536）

`CGI.escape` は**フォーム用の符号化**で、空白を `+` にする。
URL の道筋（パス）では `%20` でなければならない。

```
/api/rest_v1/page/summary/Mycenaean+Greece   → 404
/api/rest_v1/page/summary/Mycenaean%20Greece → 200
```

**記事が存在しても、空白を含む語は全て引けていなかった。**
日本語には語中の空白が無いため、日本語版だけを試していると気づけない。

`Mycenaean Greece が引けない` を「曖昧一致の問題」と誤診しかけたが、
実際の HTTP 応答を確かめたことで正体が分かった。
**症状から原因を推測せず、実際の応答を見ること。**

## 8. 残した課題

- **A群の巨大PNG（1.1〜2.2MB）が元画像として残っている。**
  サムネイルが入ったので一覧は軽いが、詳細を開くと 2MB を読む。
  差し替えは既存データの上書きになるため見送り。別タスク。
- **Neon の scale-to-zero による復帰待ち。** 休止明けの最初のリクエストだけ
  1本あたり約109ms になる（通常は 2.4ms）。always-on 化はコスト増になるため保留。
  目立つようなら料金影響を試算してから相談する。
- **プロパティ札の完全な詰め表示（masonry）。** CSS の段組みに寄せると
  札の横幅変更（2〜3列ぶん）と両立しない。横幅変更を優先し、
  `items-start` で「無駄に高さが伸びる」ぶんだけ解消した。
