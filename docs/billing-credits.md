# クレジットと課金の設計

このサービスのクレジットは「画像1枚 = 1クレジット」を単位にした前払いの残高です。
値段・期限・無料枠は、崩れても画面では気づけず、使われるほど損をするだけになります。
そのため定義を1か所に置き、性質をテストで守っています。

- 定義: `backend/app/services/billing/catalog.rb`
- 検査: `backend/spec/services/billing/catalog_spec.rb`

値段や枚数を変えるときは `Catalog` を直してください。`db/seeds.rb` には書きません。

---

## 1. 原価と採算の考え方

| | 値 | 置き場所 |
|---|---|---|
| 画像1枚の原価（見立て） | ¥9（実費は8円台。円安ぶんの余裕込み） | `Catalog::COST_PER_CREDIT` |
| 決済手数料 | 3.6%（日本のカード） | `Catalog::STRIPE_FEE_RATE` |
| 最低粗利率 | 25% | `Catalog::MIN_MARGIN` |

**見立てを実費より高く置く理由**: 実費は円安の影響で ¥8 を超えており、今後も上がりえます。
上振れしてから慌てて値上げすると利用者の信頼を損なうので、はじめから安全側（¥9）で置き、
そこから利益が残る価格にしています。**余裕は原価の側に持たせています。**

**最低粗利率 25% の根拠**: 粗利 25% は手数料後の受取が1枚あたり ¥12 以上を意味し、
実費が ¥11 まで上がっても黒字が保てます。見立てを ¥6 に置いていた頃は下限を 35% にしていました。
原価側で余裕を見たぶん、下限はここまで下げてよい、という関係です。

> ⚠️ **価格に合わせてこの下限を下げないこと。** 下げた時点で、この検査は何も守らなくなります。
> 下げてよいのは、上のように**原価の見立てを引き上げて余裕を移したとき**だけです。

原価はキャッシュ（`shared_medias`。同じ単語の画像は世界で1回しか作らない）でさらに下がりますが、
**測っていない値引きを前提に設計しない**ため、採算はキャッシュ0%でも成立するようにしています。

## 2. 価格

> 「画像1枚 = 1クレジット」です。画像生成の前に文章生成（説明文と情景プロンプト）を
> 1回挟みますが、**作られる画像は1枚のまま**です。文章のぶんは単語ごとに共有され（`shared_briefs`）、
> 1枚あたり0.1円に満たないため、クレジットには数えていません。

### 月額プラン

| プラン | 月額 | 付与 | 1枚あたり | 粗利 |
|---|---|---|---|---|
| free | ¥0 | 0（お試しと毎月枠は別建て） | — | — |
| standard | ¥1,480 | 100枚 | ¥14.80 | 37% |
| pro | ¥3,980 | 280枚 | ¥14.21 | 34% |
| creator | ¥9,800 | 720枚 | ¥13.61 | 31% |
| studio | ¥19,800 | 1,550枚 | ¥12.77 | 27% |

> 月額は**価格を据え置き、付与枚数で調整**しています。すでに払っている人の請求額が変わらず、
> 原価の変化を吸収できるためです。値段そのものを動かすのは、枚数では吸収しきれなくなったときに限ります。

### 買い切り（Top-up）

| | 価格 | 1枚あたり | 粗利 |
|---|---|---|---|
| 10枚 | ¥190 | ¥19.00 | 51% |
| 50枚 | ¥900 | ¥18.00 | 48% |
| 100枚 | ¥1,700 | ¥17.00 | 45% |
| 300枚 | ¥4,800 | ¥16.00 | 42% |
| 1,000枚 | ¥15,000 | ¥15.00 | 38% |

### 守っている関係

テストで固定しています（`catalog_spec.rb`）。

1. **上位ほど1枚あたりが安い**（月額・買い切りとも逆転しない）
2. **同じ単価のものを作らない**（選ぶ意味が無くなるため）
3. **すべて原価を上回る**（手数料を引いても）
4. **同じ枚数なら月額が9〜15%お得**（続けて使う人がサブスクへ寄るように）
5. **いちばん安い買い切りでも、いちばん高い月額より安くならない**

## 3. クレジットの寿命

**すべてのクレジットは、受け取ってから3ヶ月間有効**（`Billing::CreditExpiryPolicy`）。

長さはこの1か所にしか書かない。規約・画面・実装・本番データがずれないようにするため。

### 期限を置く理由

1. 受け取ったのにまだ提供していないぶん（これから出ていく原価）を抑える
2. 売上は毎月立つのに原価は使われた時に出る。離れすぎないようにする
3. **前払式支払手段は、発行から6ヶ月以内に限り使えるものなら規制の適用除外に入りやすい**

> ⚠️ 3 があるため **6ヶ月を超えないこと**。
> 法令の適用は専門家に確認してください（このドキュメントは法的助言ではありません）。

### なぜ正式公開初期は3ヶ月か

3ヶ月を恒久固定する意図ではない。この時期は

- AI API の値段
- 採用するモデル
- 為替
- 1クレジットあたりの実原価
- 消化ペース・失効率
- 粗利率

のどれもが動く。四半期ごとに実績を見て、見通しが立つなら4〜6ヶ月へ延ばす。

**短くするより延ばすほうが説明しやすい**ので、短いところから始める。
延ばすのは「増えた」と受け取られるが、縮めるのは既に配ったものを取り上げる話になる。

出どころで分けない。無料も有料も、受け取りから同じ長さ。
払っている人ほど厳しい、という逆転を作らないため。

### 大きい買い切りとの噛み合い

1,000枚パックを3ヶ月で使い切るには1日およそ11枚のペースが要る。
「まとめると安い」と言って売ったものが使い切れずに消えるのは、割引が見せかけになる。
パックの規模そのものは値段に触る話なので、別の判断として切り出してある。

### 消費の順番

**期限が近いものから使います**（`User#consumption_sources`）。

以前は「グラント → 月額分 → 買い切り」と種類で決めていたため、月末で消える月額分より先に、
まだ数ヶ月ある期限付きを使ってしまい、**消えなくてよかったぶんを失っていました**。

期限が無いもの（期限導入前に購入された古い買い切り分）は最後に回します。いくらでも待てるためです。

### 解約したとき

**付与済みのクレジットは期限まで有効**です。すでに払った月のぶんを取り上げないためです。

### 作り直し（再生成）

| 状態 | 費用 | 理由 |
|---|---|---|
| 失敗からの作り直し | **無料** | こちらの失敗。渡せていないものに課金しない |
| 出来上がったものの作り直し | **1クレジット** | 新しい画像を1枚作る。原価は初回とまったく同じ |
| 画像ファイルが失われていた場合 | **無料** | こちらの取りこぼし。`repair_item_if_media_missing` が failed へ落とす |

**半額にしていません。** 作り直しの原価は初回と同じ ¥9 で、割引の根拠が原価側にありません。
0.5クレジットにすると上位プランで逆ざやになります（studio: 0.5cr = ¥6.39 < 原価 ¥9）。

回数の上限も置いていません。1クレジットかかるなら残高が自然な歯止めになり、
「なぜ3回目は押せないのか」を説明する必要も出ないためです。

> 以前は**出来上がったものの作り直しが無料・無制限**でした。
> 同じカードを100回引き直せば ¥900 の原価が出る状態だったので、塞いでいます。

## 4. 無料枠

無料枠は**回収の当てがない支出**です。絞れるだけ絞ります。

| | 量 | 1件あたりの持ち出し |
|---|---|---|
| お試し（登録時に1回） | 3枚 | ¥18 |
| 毎月（訪れた人にだけ） | 1枚 | ¥6/月 |

1万件登録された場合の初期費用は ¥270,000 です（10枚配っていた頃は ¥900,000 でした）。

毎月分は **lazy に配ります**。残高を見にきた人にしか付与しないので、休眠アカウントには出ていきません。

### 乱用への備え（2段構え）

| 手口 | 対策 | 実装 |
|---|---|---|
| 同じ人が退会→再登録を繰り返す | 配った相手を覚えておく | `TrialGrantRecord` |
| 別々の相手が一斉に大量登録する | 1日に配る総量の上限 | `Billing::FreeGrantGuard` |

**`TrialGrantRecord`** はメールアドレスと外部認証（Google 等）の識別子を、アプリの秘密鍵から
導出した鍵で HMAC したものだけを保持します。元の情報には戻せず、照合以外に使えません。
**アカウントを削除しても残します**（そこが要点のため）。プライバシーポリシーに記載済みです。

**`FreeGrantGuard`** は1日500クレジット（`FREE_GRANT_DAILY_CAP`）を超えたら配るのを止め、
ログと Sentry に残します。全体を止めるのでまっとうな新規登録も巻き込みます。
だからこそ、**当たった時点で必ず気づける**ようにしてあります。

### 端末での判定を入れていない理由

- 指紋を採る方式は少し工夫すれば回避でき、その割に誤検知が出る
- 取得する情報の性質上、説明責任が重くなる
- IP は共有回線・モバイル回線で大量に重なり、まっとうな利用者を巻き込む

「同じ人が繰り返す」を識別子で、「別々の相手が一斉に来る」を総量で止める方が確実です。

## 5. 支払いの反映

反映の経路は2つあり、**どちらから来ても二重にならない**ようにしてあります。

```
Stripe webhook ─┐
                ├→ Billing::PaymentApplier ─→ クレジット付与
決済後の取り込み ─┘
```

冪等の鍵は **支払いそのものの id** です（買い切り = `cs_...` / サブスク = `in_...`）。
イベント id を鍵にすると、同じ支払いでも経路ごとに別の鍵になり二重に増えます。

### 自動反映

`/billing` を開いた時点で、最後の確認から10分以上経っていれば Stripe に問い合わせます
（`Billing::AutoReconciler`）。webhook は届かない・遅れる・落ちることがあり、
そのたびに人手で直すのは運営として成り立たないためです。

- 確認が失敗しても**残高表示は止めません**（見られなくなる方が困る）
- 失敗しても時刻は進めるので、叩き続けません
- 手動の「支払いを反映する」ボタンは、間隔を無視して今すぐ確認したいときの受け皿です

### 開発機での注意

Stripe の webhook 送り先は本番1つだけです。**開発機で checkout すると webhook は本番へ飛び、
ユーザーが一致せず反映されません**。上の「決済後の取り込み」があるのでローカルでも試せますが、
webhook 経路そのものを試したい場合は `stripe listen --forward-to localhost:3001/api/v1/stripe/webhook` を使います。

宛先が特定できない支払いは `[stripe webhook] UNMATCHED` としてログと Sentry に出ます。

## 6. 期限が近いときのお知らせ

`NotifyExpiringCreditsJob`（毎日 8:00）が、**7日前**と**前日**に1回ずつ知らせます。

- 買い切りは実際にお金を払っているので、黙って消すのは誠実ではありません
- 月額の当月分は毎月補充されるので**知らせません**（毎月鳴ると読まれなくなり、本当に伝えたい時に届かない）
- 近い節目と遠い節目の両方に当てはまる場合は、**近い方だけ1回**鳴らします
- 「残り◯日」は**日の単位**で見ます。秒まで見ると、ちょうど境目にあるぶん
  （1日と0.5秒後に切れる等）をどの回も拾えず、一度も知らせないまま失効させてしまいます

失効そのものは `ExpireCreditGrantsJob`（毎日 4:00）が台帳に記録します。
**お知らせを先に流す**ため、時刻の順番を入れ替えないでください。

## 7. 運営から見えるもの

`/admin` の「未使用クレジット」で、**受け取ったのにまだ提供していないぶん**を確認できます。

- 期限付き / 無期限に分けた総量
- どこに溜まっているかの内訳
- 直近30日で失効したぶん（使われずに消えた量）
- **未使用の買い切りぶんの金額換算**（受け取ったのにまだ提供していない額）

金額換算のために、購入時の支払額を台帳（`credit_transactions.amount_cents`）に残しています。
終了を計画するときや、万一の返金が要るときに、これが無いと金額を出せません。

## 8. アカウント削除・サービス終了

### アカウント削除（利用者の意思）

保有クレジットは削除と同時に消滅します。返金はしません（利用規約 第4条の7）。
自分で消す選択をしているので、これで筋が通ります。

### 解約（無料プランに戻る）

**付与済みのクレジットは期限まで有効**です（第4条の6）。
すでに払った月のぶんを取り上げないためです。

### サービス終了（当社の都合）

**終了日の6ヶ月前までに通知**します（第4条の8）。

これはクレジットの有効期限（3ヶ月）より長い期間です。つまり**通知時点で保有されている
クレジットは、終了日までにすべて自然に期限を迎えます**。返金の手続きが要りません。

告知を6ヶ月のままにしてあるのは、期限を延ばす日が来ても告知を短くしないで済むためです。

告知と同時に買い切りの新規販売と有料プランの新規申込みを停止します。

> なぜ返金ではなく告知期間で解決するのか
>
> 返金は運用が重い（Stripe の返金、部分返金の按分、税の扱い、問い合わせ対応）割に、
> 期限より長い告知期間を置いてある以上、同じ結果になります。
> やむを得ず期間を確保できない場合に備えて、返金の余地だけ規約に残してあります。

## 9. 価格を変えるときの手順

1. `Billing::Catalog` を直す
2. `bundle exec rspec spec/services/billing/catalog_spec.rb` で採算と並びを確認
3. `bundle exec rails db:seed` で Plan に反映
4. **価格（`price_cents`）を変えた場合のみ**、Stripe の Price を作り直す
   ```ruby
   Plan.where(name: [...]).update_all(stripe_price_id: nil, stripe_product_id: nil)
   Billing::SyncPlans.call(logger: ->(m) { puts m })
   ```
   Stripe の Price は後から変更できないため、新しい Price を作る運用になります。
5. 付与枚数（`credits_per_period`）だけを変えた場合は **Stripe の変更は不要**です

> ⚠️ 本番（live）へ移すときは、サンドボックスの `stripe_price_id` を空にしてから
> 本番の `STRIPE_SECRET_KEY` で `SyncPlans` を実行してください。
