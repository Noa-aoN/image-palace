# 課金の事故と再発防止

> 最終更新: 2026-08-15
>
> **このファイルは git 管理対象。** 秘密情報（API キー・署名シークレット・顧客や決済の id・
> 個人情報）は書かないこと。

日記ではなく**再発防止の索引**。症状から原因へ辿れることを優先する。

---

## 1. Webhook の宛先を間違えた

**症状** — Live の webhook を作ったのに、イベントが1件も届かない（404）。

**原因** — 実際のルートは `/api/v1/stripe/webhook` だが、`/api/v1/billing/webhook` を
案内していた。`billing` 名前空間には checkout / portal はあるが webhook は無い。

**再発防止**
- `BILLING_OPERATIONS.md` に正しい URL を明記
- 疎通確認は「署名なしで叩いて **400 が返る**こと」で行う。404 なら URL が違う

**気づき方** — Stripe ダッシュボードの配信ログが 404。アプリ側のログには何も残らない。

---

## 2. Test の顧客 id が Live に残った

**症状** — 購入ボタンを押しても決済画面へ進まない（API が 500）。

**原因** — Sandbox で決済した利用者に `cus_...`（テストモード）が残っていた。
`Billing::Customers.ensure` は既存 id をそのまま返す作りで、Live でその id を
指定して Checkout を作ると `No such customer` で落ちる。

**再発防止**
- `Customers.ensure` が**いまの鍵から引けるかを確かめ、引けなければ作り直す**
- 通信そのものが失敗したときは既存を信じる（一時的な不調で顧客を増やさない）

**自動テスト** — `spec/services/billing/customers_spec.rb` / `mode_consistency_spec.rb`

**診断** — 「いまの鍵から引けない顧客」の件数（→ `BILLING_OPERATIONS.md` の健全性確認）

---

## 3. Test の商品に税コードが無かった

**症状** — ローカルで購入すると 500。
`the product tax code is missing. Product tax code is required for Managed Payments`

**原因** — Managed Payments が有効な口座では、税コードの無い商品を line_items に
載せると Checkout Session の**作成そのものが失敗**する。税コードを付ける仕組みが
入る前に作られた商品が Test 側に残っていた。

**再発防止** — `SyncPlans` が `TAX_CODE`（`txcd_10000000`）を必ず付ける。
モードを切り替えたら `sync_plans` を流す。

**気づき方** — 決済画面に進めず、API が 500。エラー本文にダッシュボードのリンクが出る
（そのリンクの `/test/` か `/live/` で、**どちらのモードで失敗したか**が分かる）。

---

## 4. `cancel_at` を同期していなかった

**症状** — お支払い管理ページから解約したのに、アプリに「期末で解約予定」が出ない。

**原因** — Portal からの解約は、Stripe 側では `cancel_at`（期末の時刻）で予約され、
`cancel_at_period_end`（真偽値）は **false のまま**になることがある。
`SubscriptionSync` は真偽値だけを写していた。

**再発防止** — 真偽値と `cancel_at` の**どちらかが立っていれば解約予定**として扱う。

**自動テスト** — `spec/services/billing/subscription_sync_spec.rb`

**気づき方** — Stripe と DB を突き合わせると、両方 false で一致してしまう
（＝同期は動いている）。**Stripe 側の `cancel_at` まで見ないと分からない。**

---

## 5. 解約時に付与済みの CR を没収していた

**症状** — 解約すると、残っていた月額分のクレジットが即座に消えた。

**原因** — 規約は「付与された日から3ヶ月」「解約後も期限まで使える」と定めているのに、
実装が `forfeit: true` で没収していた。**実装が規約に追いついていなかった。**

**再発防止** — 没収をやめ、持ち越しの grant へ移す。期限が来れば自然に失効する。

**自動テスト** — `spec/services/billing/cancel_keeps_credits_spec.rb`（9例）

**教訓** — 規約・料金画面・FAQ・用語集を実装より先に読むこと。今回は**規約のほうが正しかった**。

---

## 6. 買い切りなのに「プラン反映待ち」が出続けた

**症状** — 買い切りは正しく反映されているのに、
「決済は完了しています。プランの反映に時間がかかっているようです。」が消えない。

**原因** — 反映の判定が**プラン名の変化しか見ていなかった**。買い切りではプランが
変わらないので「変化なし」と読まれ、ポーリング打ち切り後にあの文言へ落ちていた。

**再発防止** — 残高の増加も見る（`reflected`）。

**自動テスト** — なし（フロントの純関数として切り出し済み。UI テスト基盤が入ったら追加）

---

## 7. 返金しても CR が戻らない（**未解決・仕様として明示**）

**症状** — Stripe で返金しても、アプリのクレジットは減らない。

**原因** — `charge.refunded` を購読していない。

**現状の扱い** — **手で `adjustment` を記録して調整する**（→ `BILLING_OPERATIONS.md`）。
自動化は公開後 TODO。返金が実運用で発生してから、落ち着いて設計する。

---

## 8. 古い残高カラムが実残高を表していなかった

**症状** — クレジット履歴に残高を出そうとしたら、行が持つ値と実残高が合わない。

**原因** — `subscription_credits_after` / `topup_credits_after` は**古い入れ物の残高**で、
いまの残高の主役である期限付き grant を含まない。実データでは `0 / 18700` と
記録されている一方、そのときの実残高は `50800` だった。

**再発防止** — あの2列を残高として使わない。履歴の残高は**いまの残高から台帳の増減を
遡って積む**（`withRunningBalance`）。台帳は失効も1行として持つので、遡れば正しくなる。

**自動テスト** — `frontend/test/lib/running-balance.test.ts`
