# fix: 認証回帰防止とエラーハンドリングを強化

- 状態: 下書き
- 初回記録日: 2026-04-06
- 対象範囲: 認証

## 概要

- メール新規登録で発生していた認証エラーを修正し、signup / login / protected API / 認可の回帰防止をまとめて強化した。
- フロントのエラー文言吸収、バックエンドのフォールバック、認証フローの integration test、認可テスト、運用ドキュメントを一体で整えたコミットである。

## 症状

- メール新規登録時に `confirm_success_url` 関連のエラーで登録が失敗した。
- 一部の不正メール形式では `Email is not an email` のような backend 英語文言がそのまま UI に表示された。
- 認証まわりの回帰確認が不足しており、signup / login 後の auth headers や protected API アクセスまで固定できていなかった。

## 発生条件

- フロントエンドから `confirm_success_url` を送らずにメール signup を行うと再現した。
- signup / login の異常系や protected API まで含めた回帰チェックがない状態で認証まわりを変更すると、同種の不具合を見逃しやすい状態だった。
- 認証エラーの backend 文言バリエーションをフロントで吸収していないと、生の英語メッセージが表示された。

## 原因

- 直接原因は、`devise_token_auth` が必要とする `confirm_success_url` を frontend が送っていなかったことと、backend 側にも未指定時の安全なフォールバックがなかったこと。
- あわせて、backend が返す認証エラー文言の一部を frontend が日本語化しておらず、UI での吸収漏れが起きていた。
- 根本原因は、認証の確認観点が「登録できるか」に寄っており、「auth headers が返るか」「返却トークンで protected API に通るか」「他ユーザーのデータが見えないか」まで自動テストで固定できていなかったこと。

## 修正内容

- コミット要約: `fix: 認証回帰防止とエラーハンドリングを強化`
- `backend/app/controllers/api/v1/auth/registrations_controller.rb` を追加し、`confirm_success_url` 未指定時は `FRONTEND_URL` からデフォルト値を補完するようにした。
- `backend/config/routes.rb` で registrations controller を差し替えた。
- `frontend/src/lib/api/auth.ts` で signup 時に `confirm_success_url` を送るようにした。
- `frontend/src/lib/auth-errors.ts` と `frontend/test/auth-errors.test.mjs` で backend 認証文言の日本語化と回帰防止テストを追加した。
- `backend/test/integration/auth_flow_test.rb` で signup / login / protected API / 異常系の integration test を追加した。
- `backend/test/integration/api/v1/items_controller_test.rb` で他ユーザーの item が見えないことを固定した。
- `docs/playbook/auth-regression-checklist.md` を追加し、認証回帰の確認観点を明文化した。

## 影響範囲

- 影響を受けたのは主にメール signup、メール login、認証エラー表示、認証後の protected API アクセス、および item の owner スコープ確認である。
- Google OAuth 自体は直接の障害点ではないが、認証回帰チェックの一部として影響有無を確認すべき領域に含めた。
- 詳細な個別事象は以下の doc に分割している。
  - `docs/errors/2026-04-06_confirm_success_url未指定でメール登録に失敗.md`
  - `docs/errors/2026-04-06_Email_is_not_an_emailがそのまま表示された.md`

## 学び

- 認証の修正は、フロントとバックエンドの片側だけで防がず、両側で壊れにくくするべき。
- signup / login は「成功する」だけでは弱く、auth headers 返却、protected API アクセス、認可境界までテストで固定する必要がある。
- backend 由来のエラー文言は 1 件ずつ対症療法で直すのではなく、変換テーブルとテストで系統的に吸収する方が再発しにくい。
