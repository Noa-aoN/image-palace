# Error Docs Skill

`docs/errors/` に残す個別エラーのドラフトを起こすときは、まず以下を実行する。

```bash
./scripts/generate_error_docs.sh $ARGUMENTS
```

引数がない場合は、最近の `fix:` コミット 5 件から Gemini ベースの error doc を生成する。

## 生成フロー

スクリプトは次を行う。

1. 対象コミットを特定する
2. `collect_error_doc_context.sh` で調査材料を集める
3. Gemini API に調査材料を渡し、テンプレートに沿った本文を生成する
4. 既存ファイルに `TODO` が残っている場合は上書きする

必要なら追加で以下を読む。
- `git show <commit>:<path>` で主変更ファイル
- 変更された test ファイル
- 変更された docs ファイル
- 既存の `docs/errors/` 内で重複しそうな事例

## 記述ルール

- `TODO` は残さない
- 事実ベースで書く
- コミット差分から直接言えないことは「推定」と明記する
- 変更ファイルに書かれていない一般論で水増ししない
- `原因` は可能なら直接原因と根本原因を分けて書く
- `学び` は一般論ではなく、この不具合から得た具体的な教訓にする
- `再発防止` は追加したテスト、チェック、docs のいずれかに結びつける

## 重複時の扱い

- すでに同じ事象の詳細ドキュメントがある場合は、新しい broad なドラフトをそのまま残さない
- 既存 doc を更新するか、重複ドラフトを削除する

## 最終確認

Gemini 生成後は、少なくとも以下を見直す。

1. `概要`
2. `症状`
3. `発生条件`
4. `原因`
5. `学び`
6. `再発防止`
7. `関連テスト`

必要なら、ファイル名からコミットハッシュを外して読みやすい名前へ変更する。

運用ルールは `docs/errors/README.md` を参照する。
